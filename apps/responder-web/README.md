# MediPass Public Responder Web

React + TypeScript + Vite website opened when a responder scans a MediPass emergency QR code. The responder does not need a MediPass patient account or installed app.

Owner: Team Member 2 (see `docs/team-handoffs/`).

## What it does

- Route `/passes/:token` first calls `GET /api/v1/public/passes/{token}`.
- An active pass without a responder verification session returns `428 RESPONDER_VERIFICATION_REQUIRED`; the website then renders the responder verification gate instead of clinical information.
- Phone verification collects a self-declared responder name, optional role/organization, and an E.164 mobile number. In production SMS mode, successful OTP proves control of that phone number. It does **not** independently verify the responder's legal name, role, or organization.
- Development mode uses a clearly labelled simulated OTP and does not send an SMS.
- If phone verification is impossible during an emergency, the responder can use the explicit emergency override. That session is clearly marked unverified and records the self-declared identity plus the reason.
- After verification/override, `200` renders only the patient-authorized categories returned by the backend.
- `404` → generic "link not recognized" screen.
- `410` → expired or revoked/no-longer-available screen.
- Network failure → retryable connection-error screen. Public API requests are aborted after 10 seconds so a responder is not left waiting on the loading screen indefinitely.
- The route path intentionally matches the `publicUrl` generated by `EmergencyPassService`.

## Responder accountability

Every successful responder view includes:

- responder name, role, and organization when supplied;
- verification method;
- masked phone digits in the patient-visible audit record for phone verification;
- browser-visible device label;
- server-generated `MP-...` trace code;
- a repeating forensic watermark containing responder identity, trace code, and—during the current verified in-memory browser session—the full phone number.

The full verified phone number is intentionally kept only in page memory for the watermark. The backend audit stores only the last four digits. Browsers cannot reliably report screenshot/screen-recording events or universally disable OS-level capture, so MediPass uses visible watermarking for later correlation rather than claiming screenshot detection.

## Security notes

- No patient JWT is sent from this app. Public responder requests use only the pass token plus a short-lived `X-MediPass-Verification` token after verification.
- No cookies are sent (`credentials: 'omit'`).
- The responder verification token is kept only in component memory; it is not written to `localStorage` or `sessionStorage`.
- The scanned pass token is used only as a URL path segment and is never written to browser storage or analytics.
- Fetch requests use `cache: 'no-store'`; the backend also emits no-store/no-cache response headers.
- Unshared categories are absent from the API response. The website never infers, caches, or backfills a category the backend did not send.
- Copy/cut/context-menu and printing are restricted as best-effort browser privacy controls. These are deterrents, not OS-level screenshot prevention.

## Setup

```bash
cd apps/responder-web
npm install
cp .env.example .env
npm run dev
```

`.env`:

```text
VITE_API_BASE_URL=http://localhost:8080
```

The Spring Boot API must allow the responder origin in `CORS_ALLOWED_ORIGINS`, including the custom `X-MediPass-Verification` header.

### Responder verification backend mode

The API defaults to the development provider:

```text
RESPONDER_OTP_PROVIDER=dev
RESPONDER_DEMO_OTP=123456
```

This is suitable for the capstone demo because the UI explicitly labels it as a development simulation. For real SMS, set `RESPONDER_OTP_PROVIDER=twilio` and provide `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_VERIFY_SERVICE_SID` privately. Never commit those values.

## Testing

Automated coverage includes:

- public API contract states: `200`, `404`, `410`, `428`, network failure, unexpected status;
- 10-second stalled-request timeout;
- responder verification gate before clinical disclosure;
- no browser-storage persistence of pass/verification tokens;
- restricted categories not rendered;
- production build/type-check;
- forensic watermark containing responder, full in-memory verified phone, and trace code.

Manual release checks remain in `docs/testing/demo-runbook.md`.
